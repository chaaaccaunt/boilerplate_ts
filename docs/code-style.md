# Правила написания кода

## Область применения

Правила применяются ко всему новому и изменяемому прикладному коду проекта. Основной язык новой разработки — TypeScript.

Существующие JavaScript-файлы, включая root runner и frontend-конфигурацию, поддерживаются в текущем формате до отдельного решения об их миграции на TypeScript. Изменение существующего JavaScript не является разрешением на сопутствующую миграцию файла или соседнего кода.

## Общий стиль

- Предпочитать явные конструкции, если сокращенная запись скрывает ветвление, мутацию, обработку ошибки или преобразование типа.
- Не использовать синтаксический сахар только ради сокращения количества строк.
- Не усложнять существующий код ради замены понятной краткой конструкции на более развернутую.
- При выборе конструкции учитывать читаемость, типобезопасность и предсказуемость поведения, а не только форму записи.

## Принципы SOLID

- Новый и изменяемый объектно-ориентированный код должен соответствовать принципам SOLID в той мере, в которой они применимы к решаемой задаче.
- Класс, модуль или сервис должен иметь одну ясно определенную ответственность и одну основную причину для изменения.
- Расширение поведения предпочтительно выполнять через устойчивый публичный контракт, композицию или новую реализацию, не изменяя проверенное поведение без необходимости.
- Реализация подтипа должна сохранять контракт базового типа и не усиливать предусловия, не ослаблять постусловия и не менять ожидаемую семантику.
- Потребитель должен зависеть только от минимального интерфейса, который он фактически использует; крупные несвязанные контракты разделяются по ответственности.
- Высокоуровневая бизнес-логика не должна зависеть от деталей транспорта, базы данных и другой инфраструктуры; зависимости направляются к абстракциям и передаются явно.
- Применение SOLID не является основанием для создания лишних интерфейсов, классов, слоев или фабрик. Абстракция вводится при наличии реальной границы ответственности, нескольких реализаций, необходимости изоляции инфраструктуры или подтвержденной точки расширения.

## Иммутабельность

- Иммутабельность обязательна на публичных границах модулей, но не запрещает локальную контролируемую мутацию.
- Переменные объявляются через `const`, если повторное присваивание объективно не требуется.
- Функции и методы по умолчанию не изменяют полученные аргументы, глобальное и разделяемое состояние.
- Локальная мутация нового объекта или коллекции допустима, если она не наблюдается снаружи и не нарушает публичный контракт.
- Публичные свойства и коллекции описываются через `readonly`, `Readonly<T>` и `ReadonlyArray<T>` в применимой части.
- Внутреннее изменяемое состояние класса не передается наружу по ссылке.

Пример допустимой локальной мутации:

```ts
function normalizeUsers(users: ReadonlyArray<User>): User[] {
  const result = users.slice();

  result.sort(compareUsers);

  return result;
}
```

Исходный аргумент не изменяется, а локальная мутация новой коллекции не выходит за границы функции.

## Асинхронный код

- Для линейных асинхронных операций предпочтительны цепочки `Promise` с `.then()` и `.catch()`.
- `async/await` используется, если ветвление, циклы, несколько зависимых результатов или объем цепочки делают Promise-запись менее читаемой.
- Выбор `async/await` должен улучшать понимание кода и не служит основанием переписывать соседнюю реализацию.
- `try/catch` добавляется не вокруг каждого `async/await`, а там, где ошибку можно обработать, дополнить значимым контекстом, преобразовать в доменную ошибку или передать через границу слоя.
- Для одной логически связанной Promise-цепочки предпочтителен один общий `.catch()` после последнего `.then()`.
- Промежуточный `.catch()` используется только для локального восстановления, компенсации или преобразования ошибки.
- Если после локальной обработки выполнение нельзя безопасно продолжить, ошибка повторно выбрасывается через `throw` или возвращается `Promise.reject()`.

Предпочтительный линейный вариант:

```ts
loadData()
  .then(processData)
  .then(saveData)
  .catch(handleError);
```

## Доменные ошибки и сообщения

- Неизвестная ошибка преобразуется в типизированную доменную ошибку на подходящей границе слоя.
- Доменная ошибка содержит стабильный `code`, `domain`, название операции и исходную причину в `cause` или эквивалентном поле.
- Место возникновения определяется по stack trace. Ручное строковое поле с именем функции не используется как единственный источник места ошибки.
- При повторном выбрасывании сохраняются исходная причина, домен и полезный диагностический контекст.
- Ошибка журналируется один раз на инфраструктурной границе, если дополнительное журналирование не требуется отдельным сценарием.
- Техническое сообщение предназначено для журнала и отладки и может содержать домен, операцию и диагностический контекст.
- Пользовательское сообщение формируется на границе UI или API, остается безопасным и не раскрывает stack trace, внутреннее устройство системы и чувствительные данные.
- Низкоуровневая библиотека не обязана формировать пользовательское сообщение, если она не отвечает за представление результата пользователю.

Пример преобразования ошибки:

```ts
loadData()
  .then(processData)
  .then(saveData)
  .catch((error: unknown) => {
    throw toDomainError(error, {
      code: "DATA_SAVE_FAILED",
      domain: "data-processing",
      operation: "load-and-save-data",
    });
  });
```

## Типы и контракты

- Backend/runtime global declarations размещаются в корневом `@types` и используют существующие предметные namespaces, включая `iLibs` и `iDatabase`.
- JSON-safe DTO/API/state contracts между frontend и backend размещаются в `shared/@types` и не импортируют runtime-код.
- Frontend-local declarations размещаются внутри `monolith/src`, а package-local backend declarations — внутри `services/<name>/src/@types` или `gateways/<name>/src/@types`, если тип не является общим контрактом.
- `abstract class`, обычные классы и runtime-`enum` считаются исполняемым кодом и размещаются в соответствующем модуле реализации.
- Локальный тип остается рядом со своим потребителем, пока не появляется предметно обоснованный общий контракт.
- Типовые модули группируются по предметной области, а не по месту первого использования объявления.
- Не создавать разные объявления для одной сущности без различия их контрактов или назначения.

## Переиспользуемый код

- Общая backend infrastructure размещается в корневом `libs` после появления стабильного общего контракта.
- Само по себе внешнее сходство или второй потребитель не являются достаточным основанием для преждевременного объединения реализаций.
- Публичный API `libs` экспортируется через `libs/index.ts`; прикладной backend-код импортирует runtime values через `@/libs`.
- Публичные типы `libs` объявляются в namespace `iLibs` в `@types/libs.d.ts` и используются без прямых импортов из внутренних файлов.
- Внутри `libs` допускаются прямые относительные импорты, если они делают зависимости прозрачнее и не создают циклических зависимостей.
- Внутренние реализации, не входящие в публичный контракт, не экспортируются из публичной точки входа.
- Экспортируемые функции не изменяют переданные им объекты и коллекции.
- Из `libs` не экспортируется изменяемое разделяемое состояние.
- Публичные классы не предоставляют внешнему коду изменяемые ссылки на внутреннее состояние.
- `Object.freeze()` применяется к конфигурациям и экспортируемым константам только тогда, когда runtime-иммутабельность является частью их контракта.
- Классы и прототипы не замораживаются по умолчанию.

## Публичные контракты и границы модулей

- Публичный контракт модуля отделяется от внутренней реализации и экспортируется через явно определенную точку входа.
- Внешний потребитель не импортирует внутренние файлы модуля в обход его публичной точки входа.
- Внутренние классы, функции и типы не экспортируются без подтвержденной потребности внешнего потребителя.
- Для каждого правила, лимита и параметра определяется один источник истины. Лимиты загрузки, имена cookie, URL сервисов и другие настройки не дублируются между слоями без технической необходимости.
- Новый пакет, сервис или отдельный процесс создается только при наличии ясной границы ответственности, самостоятельного жизненного цикла, требований к изоляции или масштабированию. Внешнее сходство модулей само по себе не является основанием для их физического разделения.
- Frontend импортирует backend-контракты только из `shared/@types` и не зависит от `libs`, `models`, services или gateways.
- Gateway отвечает за публичную HTTP/WebSocket boundary, а service — за бизнес-логику и доступ к данным; service не формирует HTTP responses и не выбирает HTTP status codes.

## Конфигурация

- Конфигурация приложения читается и проверяется на границе запуска, после чего передается потребителям в типизированном виде.
- Отсутствие обязательного параметра приводит к понятной ошибке запуска. Для секретов, реквизитов доступа и production-настроек не используются скрытые или небезопасные значения по умолчанию.
- Секреты, реальные пароли, токены и production-реквизиты не хранятся в репозитории.
- Пример конфигурации содержит полный перечень поддерживаемых параметров, использует корректную UTF-8-кодировку и синхронно обновляется с загрузчиком конфигурации.
- Клиентская конфигурация не содержит серверных секретов и иных значений, которые нельзя раскрывать пользователю.

## Границы backend-слоев

- Контроллер отвечает за транспортную границу: принимает запрос, запускает валидацию и проверку доступа, вызывает прикладной сервис и формирует ответ.
- Бизнес-правила, работа с доменными сущностями и координация операций размещаются в прикладном или доменном сервисе, а не в транспортном контроллере.
- Аутентификация подтверждает личность или сессию, а авторизация отдельно проверяет право на конкретную операцию.
- Изменяющие, административные и чувствительные операции проверяют необходимые разрешения на сервере. Скрытие элемента интерфейса не считается контролем доступа.
- Для отзыва сессий и токенов явно определяется момент прекращения доступа. Поведение при отзыве, блокировке пользователя и изменении его прав документируется и проверяется тестами.

## Клиентские границы

- Данные из cookie, `localStorage`, URL, DOM и ответов API считаются недоверенными до проверки.
- Роли и разрешения на клиенте используются для представления интерфейса, но не заменяют серверную авторизацию.
- Сетевое поведение централизуется в API-клиенте или соответствующем инфраструктурном модуле: формат ответа, credentials, базовый URL и преобразование транспортных ошибок не реализуются заново в каждом компоненте.
- UI-компонент не должен напрямую знать детали транспорта, хранения или серверной конфигурации, если их можно скрыть за API-модулем или моделью состояния.
- Динамический HTML из недоверенного источника не вставляется без очистки. Экранирование текста не заменяет проверку URL, допустимых протоколов и структуры содержимого.

## Наблюдаемость и журналирование

- Значимые изменяющие операции журналируются на инфраструктурной границе с названием операции, идентификатором запроса и безопасным контекстом объекта воздействия.
- Пароли, токены, cookie, ключи, авторизационные заголовки и другие секреты удаляются или маскируются до передачи в журнал.
- Персональные данные включаются в диагностический контекст только в минимально необходимом объеме и при наличии основания.
- Одна ошибка не журналируется повторно в каждом слое без отдельной диагностической причины.

## Файлы и внешние процессы

- Недоверенный идентификатор или имя файла не используется напрямую как путь. Итоговый путь строится из проверенных частей и должен оставаться внутри разрешенного каталога.
- Для загрузок задаются применимые ограничения общего размера запроса, количества файлов и размера отдельного файла до полной обработки содержимого.
- MIME-тип и имя файла, переданные клиентом, не считаются подтверждением фактического формата файла.
- Внешний процесс запускается без shell-интерполяции: путь к исполняемому файлу и аргументы передаются отдельно.
- Пользовательское значение не включается в готовую командную строку. Если использование shell неизбежно, входные данные ограничиваются явным разрешенным набором значений и решение отдельно проверяется на инъекции.

## Миграции данных

- Миграции имеют уникальные упорядочиваемые имена, выполняются в определенном порядке и учитываются в служебном журнале или таблице.
- Уже примененная миграция не изменяется задним числом. Исправление выполняется новой миграцией.
- Различия поддерживаемых СУБД выражаются явно и проверяются для каждого заявленного диалекта.
- Миграция данных предусматривает безопасное поведение при частичном выполнении, повторном запуске и несовместимой версии схемы в применимой части.

## Защита реализации и входных данных

- Типизация, `readonly` и `Object.freeze()` не считаются самостоятельной защитой от выполнения вредоносного кода.
- Запрещается использование `eval`, `new Function` и других способов динамического выполнения непроверенных строк как кода.
- Данные из HTTP-запросов, файлов, переменных окружения, хранилищ, очередей и внешних интеграций проверяются на соответствующей границе системы.
- Для внешних данных используется схема с явным перечнем разрешенных полей; неизвестные поля отбрасываются или отклоняются.
- Доменные объекты создаются из проверенных полей, а непроверенная полезная нагрузка не объединяется напрямую с конфигурацией, публичным API или экземплярами классов.
- Обработка объектов из недоверенных источников должна исключать изменение прототипов через `__proto__`, `prototype`, `constructor` и эквивалентные пути.
- Десериализация внешних данных не должна создавать исполняемый код, экземпляры произвольных классов или изменять прототипы.
- Зависимости фиксируются lock-файлом, проверяются и обновляются контролируемо.
- Критическая инфраструктура — авторизация, права доступа, валидация, файловые пути, миграции, преобразование ошибок и внешние интеграции — покрывается автоматизированными тестами соразмерно риску.
